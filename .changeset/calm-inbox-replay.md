Support issuer-scoped idempotency keys on ordinary single inbox issuance by reusing the existing durable batch admission, leases and encrypted replay records. Unkeyed and managed-refresh requests retain their existing paths. Keyed ordinary requests require the existing inbox queue configuration. Each keyed request keeps one durable decision (a new `InboxBatchRequest` node with a uniqueness constraint on `id`, created on start like the existing inbox batch constraints; no existing data is rewritten): of the items admitted for a request before a delivery, a refusal or a replayed success, at most one may issue, and the decision is removed only after every job of the request is gone. Deployment precondition: this holds only once every HTTP and queue process runs this version and every keyed single-call item admitted by an earlier build is settled; a queue worker of an earlier version does not check the decision, and a job admitted by an earlier build carries no ordinal. No built-in check reports this: version skew is visible only in the deployment, and unsettled earlier items can be counted with `MATCH (b:InboxBatch)-[:HAS_ITEM]->(i:InboxBatchItem) WHERE b.requestId STARTS WITH 'inbox.issue:' AND b.requestSeq IS NULL AND i.state IN ['QUEUED', 'PROCESSING'] RETURN count(i)` (0 = none left).
