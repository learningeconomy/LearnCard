- Original token survives store/read/export and second verification/refresh; display metadata cannot substitute for verified claims.
- Tests cover VCDM 1.1 claim mapping, the explicitly supported VCDM 2.0 securing profile, expiration renewal, malformed/oversized responses and runtime parity.

## Design decisions and verification policy

- The signed compact token is the source for all security-sensitive metadata. Never verify a token then compare an unrelated mutable display object's ID/issuer/subject/refreshService.
- Preserve JSON behavior and public result conventions; add a typed verified-normalization path instead of pretending decoded projections are verified. Existing JwtProof2020/proof.jwt and jwt-vc-json envelopes need round-trip handling and tamper tests.
- Reject unsupported algorithms (including none and symmetric confusion), malformed headers/claims and contradictions. Use the existing verifier and key authorization, not decode-only or ad hoc crypto.
- VCDM 1.1: define precise iss/issuer, sub/credentialSubject.id, jti/id, nbf/issuanceDate, iat and exp/expirationDate mapping; compare equivalent timestamps semantically. nbf and iat may legitimately differ: do not blindly require equality; specify precedence and independent validation. Reject ambiguous multi-subject bindings.
- VCDM 2.0: establish an explicit supported securing profile in Task 1 from actual fork behavior and standards. Do not label legacy vc-claim wrapping as general JOSE/COSE conformance. Unsupported profiles must fail clearly; record any ticket blocker instead of claiming complete V2 support.
- Expired held credentials may renew only after signature, issuer authorization and claim binding pass. Normal verification and replacements must retain temporal validity requirements. Do not suppress arbitrary verifier error strings or globally relax checks. Prove an invalid signature on an expired token cannot contact the endpoint.
- Verify held credentials before network access. Preserve timeout, streamed byte cap, redirects, DNS/IP/SSRF validation, credential status/schema behavior and existing default checks.
- Standard JSON may omit IDs on both versions. If an ID exists its stability remains required. Managed credentials require stable nonempty IDs. Issuer/subjects and rollback checks run on verified normalized data for JWT inputs and responses.
- A storage round trip must retain the exact compact token and every subsequent verification/refresh must rederive authoritative claims. Test altered display metadata and a second refresh.
- Initial algorithm/key-resolution support must be established by tests in both runtimes; Ed25519 did:key is the mandatory real fixture baseline. Narrow and document unsupported JWT algorithms without regressing existing JSON cryptosuites.
