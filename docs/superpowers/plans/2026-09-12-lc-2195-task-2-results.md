## Delivered contract

### Typed verified-normalization API

New module `packages/plugins/vc/src/verifyCredentialJwt.ts` exports:

- `extractCompactJwt(input)` — returns the exact compact JWS bytes for a raw
  token, a `{ format: 'jwt-vc-json', data }` storage envelope, or a legacy
  `JwtProof2020`/`proof.jwt` projection; `undefined` for the JSON-LD path.
- `verifyCredentialJwt(initLearnCard, input, options?)` — returns a
  discriminated union:
  - `{ verified: true, token, credential, metadata }` where `token` is the exact
    verified bytes, `credential` is the authoritative normalized VC (derived
    only from the verified payload, with a `JwtProof2020`/`proof.jwt` envelope
    carrying the token), and `metadata` is token-derived
    (`version`, `profile`, `issuer`, `subjectIds`, `id`, `issuedAt`,
    `notBefore`, `expiresAt`, `algorithm`, `keyId`).
  - `{ verified: false, check: { checks, warnings, errors } }` — existing
    `VerificationCheck` convention.
- `getVerifiedCredentialTemporalStatus(verified, at?)` — renewal-specific
  temporal API (`'valid' | 'expired' | 'not-yet-valid'`).

`initLearnCard` must be the DIDKit-backed dependent-methods object injected into
the VC plugin (never the merged top-level LearnCard), so the call cannot recurse
into the VC plugin's own `verifyCredential`.

### Claim reconciliation policy (implemented)

Registered claims are reconciled against the embedded `vc` claim on the decoded
payload. Structural reconciliation only ever REJECTS; the normalized credential
is not returned until DIDKit reports a verified signature.

| Concern | Policy |
| --- | --- |
| issuer | `iss` (non-empty string) must equal embedded `issuer`/`issuer.id` when both exist; embedded-only issuer allowed; missing issuer fails |
| id | `jti` (non-empty string) must equal embedded `id` when both exist |
| subject | `sub` must equal the single embedded subject id; array-valued subjects with `sub` are ambiguous and fail; `sub` with no embedded subject creates `{ id: sub }` |
| issued-at | `iat` takes precedence over `nbf`; when the embedded timeline exists and `iat` is present they must be equal to the second; `nbf` may differ from `iat` and is independently validated |
| expiration | `exp` must equal the embedded expiration timeline when both exist |
| ranges | issuance after expiration, or `nbf` after `exp`, fails |
| NumericDates | `iat`/`nbf`/`exp` must be finite numbers; embedded dates must parse |
| profile | only VCDM 1.1 and VCDM 2.0 (legacy JOSE `vc`-claim wrapping) contexts are accepted; anything else fails clearly |
| algorithm | `alg` must be present; `none`/`HS*` are rejected before the verifier is called; remaining algorithms are delegated to DIDKit's signature + key authorization |
| key binding | an absolute `did:` `kid` must belong to a `did:` normalized issuer |
| required fields | payload `vc` must be an object with a usable `type` |

The V2 profile is explicitly labelled `vc-jwt-2.0-legacy` and is not documented
as general JOSE/COSE conformance (matching Task 1).

### Real-token matrix executed

Both positive and negative cases use generated Ed25519 `did:key` fixtures. The
positive/conflict tokens are signed with the real `jose` EdDSA signer using the
same key DIDKit resolves, so the signature is genuinely valid.

- VCDM 1.1 and VCDM 2.0 real issuer-issued tokens verify and normalize.
- Raw token, `jwt-vc-json` envelope and legacy `JwtProof2020` projection all
  yield the same exact token and metadata.
- Display mutation (issuer, id, dates, subject) does not change the verified
  metadata or normalized credential.
- Forged signature, unauthorized signing key and foreign `kid` fail closed.
- Matching duplicate, registered-only, and `iat`/`nbf`-differing claims accept;
  conflicting `iss`/`jti`/`sub`/`iat`/`exp`, ambiguous multi-subject `sub`,
  malformed NumericDates and unsupported context fail with precise errors.
- Expired and not-yet-valid tokens fail (temporal checks are never relaxed).
- `alg=none` and `HS256` are rejected before the verifier is called (spy
  assertion).
- Store (`toStoredCredential` → `jwt-vc-json`/exact token), read
  (`projectEnvelopeToDisplayVc` → `proof.jwt`) → second verification asserts the
  exact token bytes and identical trusted metadata; a JSON serialization round
  trip also retains the token.

## Store/read/export trace

`packages/learn-card-base/src/helpers/credentialRefresh.ts` reads the held
credential via `wallet.read.get(current.uri)` (line 173), calls
`wallet.invoke.refreshCredential(vc, ...)` (line 200) and uploads the returned
candidate via `wallet.store.LearnCloud.uploadEncrypted(result.credential)`
(line 246). Because the verified candidate carries the compact token under
`proof.jwt`, both the initial held credential and the replacement survive the
storage round trip and are re-derived from the token on the next verification.
`projectJwtVcCompactToVc` in `@learncard/helpers` is the read-time display
projector that re-attaches the token. Synchronous display decoding in that
projector remains explicitly unverified; trust is only granted by
`verifyCredentialJwt`.

## Limitations / blockers

1. **Task 3 blocker (inherited):** the pinned DIDKit/SSI primitive enforces
   `nbf`/`exp` unconditionally inside `jwt_matches`, so an expired-but-valid
   held token cannot currently be distinguished from an invalid one. Task 3 must
   apply the minimal pinned-fork temporal-policy opt-in documented by Task 1
   before renewing an expired token. `getVerifiedCredentialTemporalStatus` is
   provided for that path but is not used to authorize renewal yet.
2. Only Ed25519 `did:key` is exercised as a positive real fixture. Other JWT
   algorithms/key-resolution methods are delegated to DIDKit and are not claimed
   supported; unsupported/symmetric/unsigned algorithms fail closed.
3. VCDM 2.0 support is the legacy JOSE `vc`-claim wrapping profile only.
4. `packages/learn-card-types/src/credential-refresh.ts` was intentionally left
   unchanged; Task 3 may need to widen refresh response/input types for
   `text/plain` compact bodies.
5. SD-JWT compact forms are not handled or redesigned here.
6. `dualmem` reads were unavailable (`no API key: set GEMINI_API_KEY or
   GOOGLE_API_KEY`); no memory was persisted.
