## Delivered contract

### Verify and normalize before endpoint selection or network access

`packages/plugins/vc/src/refreshCredential.ts` now derives a typed
`VerifiedView` for both the held credential and the candidate:

- JWT-backed inputs (raw compact JWS, `jwt-vc-json` envelope, legacy
  `JwtProof2020`/`proof.jwt` projection) go through `verifyCredentialJwt`
  against the plugin's DIDKit dependency (`_initLearnCard`). Every
  identity/stability/freshness decision uses `metadata.issuer`,
  `metadata.subjectIds`, `metadata.id`, `metadata.issuedAt` (rollback),
  `metadata.expiresAt` and `metadata.notBefore`.
- JSON/JSON-LD inputs keep the existing `_learnCard.invoke.verifyCredential`
  path; the verified credential itself is the authoritative view.
- The held credential is verified and normalized **before**
  `getSupportedRefreshService` is called, so the signed token's
  `refreshService` — never a mutable display object's — selects the endpoint.
  Managed `LearnCardCredentialRefresh2026` still requires a stable non-empty
  verified ID before any fetch.
- The success predicate now accepts the JWT check `'JWS'` as well as the
  JSON-LD check `'proof'`; warnings and errors still fail closed.

### text/plain standard adapter, protocol distinction preserved

- `text/plain` compact bodies are accepted **only** when the held credential's
  verified `refreshService.type === '1EdTechCredentialRefresh'`. A managed
  service receiving `text/plain` fails `MALFORMED_RESPONSE`.
- Content-Type is parsed deliberately (`parseContentType`): media type is
  lower-cased, parameters are unquoted, and a `charset` parameter must name
  `utf-8`/`utf8`/`us-ascii`/`ascii` or the response is malformed. `text/plain`
  is advertised in `Accept` only for the standard service; the existing JSON
  media types and the managed encrypted/DID-auth flow are unchanged.
- Standard responses remain bare credentials, never LearnCard envelopes. A
  managed JWE/JWE-envelope advertised by a standard service is still rejected.
- The returned `result.credential` for a JWT candidate is the normalized
  credential carrying `proof.jwt = <exact token>`, so the LearnCloud
  `uploadEncrypted(result.credential)` persistence path retains the signed
  bytes and the next verification re-derives authoritative claims.

### Temporal policy

- `temporalStatusOf` classifies a verified view as `valid`, `expired` or
  `not-yet-valid` from authoritative fields only.
- A `not-yet-valid` **held** credential never initiates a refresh
  (`INVALID_PROOF`, zero fetches).
- A replacement must be temporally `valid`: expired or future replacements fail
  `INVALID_PROOF` before identity/rollback decisions.
- Expired **JSON-LD** held credentials may renew, because their signature,
  issuer authorization and claim binding were verified before any fetch; an
  invalid signature on an expired JSON held credential fails closed with zero
  network requests (explicitly tested).
- Expired **compact-JWT** held renewal is blocked by the pinned verifier (see
  below); the code path is fail-closed and tested as such.

### Helper addition

`packages/learn-card-helpers/src/credential-refresh.ts` gains

(useful with both JSON-LD and token-derived views). The refresh primitive uses
it for JSON views; Task 2's `metadata.subjectIds` is used for JWT views.

## Expired-held renewal blocker (inherited)

Task 1 documented that `ssi-vc::jwt_matches` (`filter_proofs` →
`decode_verify_jwt`) enforces `nbf` against `created`/now and `exp` against
`Utc::now()` unconditionally, with no option in the pinned fork to verify the
signature, issuer authorization and claim binding while deferring the temporal
predicate. The pinned artifact returns `{"checks":[],"warnings":[],"errors":
["No applicable JWS or proof"]}` for both an expired valid token and an
invalid/unmatched signature, so the two cannot be distinguished from the
wrapper.

Consequently, for a signature-valid but expired compact VC-JWT held credential,
`verifyCredentialJwt` fails and `refreshCredential` returns
`{status:'failed', code:'INVALID_PROOF'}` **without any network request**. This
is the safe behavior, but it does not meet the "valid expired held token may
renew" criterion. The minimal fix remains Task 1's Option 1: thread an opt-in
temporal policy (default `false`) through `LinkedDataProofOptions` →
`filter_proofs` → `jwt_matches` and rebuild the WASM and native artifacts.
Patching `lib/didkit`/`lib/ssi` and committing a WASM/`.node` artifact built
from an unpushed fork commit was judged out of scope: the parent repository
gitlinks cannot reference a local-only submodule commit, and shipping a binary
whose source commit is not obtainable would break artifact provenance for
Task 4. No fork change, no WASM rebuild and no native rebuild were performed.

### Real-signature refresh matrix executed (Ed25519 `did:key`)

Both positive and negative cases use tokens issued by the real DIDKit WASM
issuer with the same key DIDKit resolves, and are served over the mocked
guarded transport.

- Valid VCDM 1.1 and supported VCDM 2.0 compact VC-JWT refresh from a
  `text/plain` 1EdTech endpoint; exact replacement token preserved under
  `proof.jwt`; `Accept` advertises `text/plain`.
- `text/plain; charset=UTF-8` accepted; `text/plain; charset=utf-16` rejected
  `MALFORMED_RESPONSE`.
- Display metadata mutation (id, issuer, subject, issuance date and
  `refreshService` pointing at `attacker.example`) does not change the verified
  identity or the endpoint actually contacted (verified token service URL).
- Forged held signature → `INVALID_PROOF` with **zero** network requests.
- Expired held compact JWT → `INVALID_PROOF` with zero network requests
  (documented blocker; safe fail-closed).
- Two successive refreshes through a serialize → re-project persistence round
  trip, asserting the exact compact token and re-derived metadata each time.
- Validly-signed replacement with changed issuer → `ISSUER_MISMATCH`; changed
  holder or credential ID → `ID_MISMATCH`; older verified issuance time →
  `ROLLBACK`.
- Forged replacement and expired replacement → `INVALID_PROOF`.
- Non-JWT and oversized `text/plain` bodies → `MALFORMED_RESPONSE`.
- `text/plain` rejected for a managed service; managed JWT held credential
  without a stable ID rejected `ID_MISMATCH` before any fetch.
- JSON-held → JWT replacement and JWT-held → JSON replacement with the same
  verified identity both update; standard ID-less VCDM 1.1 JSON refresh.
- Expired JSON-LD held credential with a verifying proof renews; with a failing
  proof it fails `INVALID_PROOF` with zero network requests.

All 74 pre-existing `refreshCredential` tests (SSRF, redirects, timeout,
streamed byte cap, managed DID-auth challenge replay/origin binding, JWE

   (`vc-jwt-2.0-legacy`).
