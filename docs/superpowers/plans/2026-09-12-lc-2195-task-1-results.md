## Supported contracts (handoff to Task 2)

### Public API

- `didkit` plugin: `verifyCredential(credential: VC | string, options?: ProofOptions): Promise<VerificationCheck>`.
  - A `string` input is treated as a compact JWS and is passed to DIDKit
    byte-for-byte (never `JSON.stringify`d). `options.proofFormat` must be
    `'jwt'`; no context map is built.
  - An object input keeps the existing JSON-LD/LDP path with the context map.
- `issueCredential` with `options.proofFormat === 'jwt'` returns the compact JWS
  string (still typed `VC` for backward compatibility, matching the existing
  `issuePresentation` convention); otherwise a JSON credential object.
- Native addon export signatures are unchanged; only dispatch and result
  semantics changed. `verifyPresentation` now accepts `proofFormat` directly and
  falls back to the historical `eyJ` heuristic when it is absent.

### Result shape

`{ checks: string[]; warnings: string[]; errors: string[]; status?: StatusCheckEntry[] }`.
Successful JWT verification reports `checks: ["JWS"]`. Verification failures are
string entries in `errors`; malformed options (e.g. unknown `proofFormat`) reject
the promise.

### VCDM 1.1 registered/embedded claim mapping (`ssi-vc::Credential::from_jwt_claims`)

| JWT claim | Credential field | Notes |
| --------- | ---------------- | ----- |
| `iss`     | `issuer`         | must be URI form or `InvalidIssuer` |
| `sub`     | `credentialSubject.id` | only when a single subject, else `InvalidSubject` |
| `jti`     | `id`             | |
| `iat`     | `issuanceDate`   | takes precedence over `nbf` |
| `nbf`     | `issuanceDate`   | used only when `iat` is absent |
| `exp`     | `expirationDate` | |
| `vc`      | embedded credential | top-level registered claims override embedded `vc` fields **silently** |

The pinned primitive does **not** detect conflicting registered vs embedded
claims; it lets registered claims win. Task 2 must add explicit contradiction
detection on the verified claims.

### VCDM 2.0 securing profile

The pinned suite uses the legacy JOSE wrapping profile: a compact JWS whose
header carries `alg` and `kid` and whose payload carries top-level registered
claims plus a `vc` claim holding the credential. VCDM 2.0 fixtures
(`@context: https://www.w3.org/ns/credentials/v2`, `validFrom`/`validUntil`)
verify under this profile. This is **not** general VC-JOSE-COSE conformance and
must not be documented as such. Unsupported profiles/formats fail at options
deserialization or signature verification.

### Algorithms and key resolution

- Signature algorithm is taken from the JOSE header and verified by
  `ssi_jws::verify_bytes_warnable` against the key resolved from `kid`.
- Issuer authorization: `filter_proofs` restricts allowed verification methods to
  the issuer DID's assertion-method keys when the issuer is a DID.
- Tested baselines (both runtimes): Ed25519 `did:key` / `EdDSA` succeeds;
  `alg: none` fails closed; HS256 symmetric confusion fails closed; unknown
  `proofFormat` rejects. Other JWT algorithms are not yet claimed supported and
  must be narrowed/documented by Task 2.

### Temporal policy (critical handoff)

`ssi-vc::jwt_matches` (called from `filter_proofs` inside `verify_jwt`) enforces
`nbf` against `options.created`/now and `exp` against now, unconditionally.
There is no option in the pinned fork to verify signature/claims while skipping
the temporal predicates. An expired compact token returns:

```
{"checks":[],"warnings":[],"errors":["No applicable JWS or proof"]}
```

which is indistinguishable from an invalid or unmatched signature. Task 3's
"valid expired held token may renew" therefore **cannot be implemented against
the pinned fork unchanged**.

Minimal necessary fork change (one of):

1. Thread an opt-in temporal policy through `LinkedDataProofOptions` (or a new
   `verify_jwt_with_options`) into `jwt_matches`, so callers can verify
   signature + issuer authorization + claim binding while evaluating expiry
   themselves; or
2. Expose a dedicated `decode_verify_jwt`-style export that returns the parsed
   verified credential plus a distinct temporal status without weakening the
   default `verify_jwt` path.

Option 1 is the smallest: add a boolean (default `false`) to
`JWTOrLDPOptions`/`LinkedDataProofOptions`, store it through `filter_proofs`,
and guard only the `exp`/`nbf` predicates in `jwt_matches`. Do not use
`ssi_jwt::decode_verify` or hand-rolled JWS parsing for this — that would bypass
issuer/key authorization and conflict with the design policy.
