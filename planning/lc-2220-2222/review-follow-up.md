## Privacy and recovery boundaries

The local cache contains only the holder-encrypted settings snapshot. Its key identifies the holder and the feature locally; it is not a Cloud index, a receipt, or verifier metadata. If browser storage is cleared or a new device has no snapshot, sending silently skips recording until the owner opens private history there. A local snapshot does not grant write authority by itself: current encrypted Cloud consent must match after transport. Cross-tab/device preference changes therefore cannot authorize a stale receipt, though a stale disabled cache may miss recording until refreshed.

Unknown schemas/decryption failures are isolated. Validated receipt records can still be displayed and deleted individually. Routine maintenance retains unreadable documents and recent other-generation receipts; the cleanup warning and explicit Clear provide a recovery path. Clear preserves readable consent; if an unreadable record could be settings, recording is disabled rather than inferred. Failed deletion still reports incomplete cleanup. Never treat an empty Cloud result as proof to erase another generation.

Cloud pagination orders by ObjectId, not a shared monotonic revision. Different service instances can create IDs within the same second that do not reflect the order of user actions. Concurrent toggles/clears are not globally atomic or guaranteed last-action-wins. Consent revision checks invalidate stale attempts; they do not supply cross-device CAS. A server ordering/version primitive would be a separate storage contract change. Retention and cleanup only run on successful access, and future-dated/unreadable data can remain longer until clocks catch up or the owner explicitly clears it.
